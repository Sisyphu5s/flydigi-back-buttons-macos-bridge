# 12 · 固件实现（RP2350 桥）

> 状态：**Generic、Vader2Pro Apple 兼容固件和电量探针均已构建并通过描述符校验；当前板保留已验证的 Apple 兼容镜像，网页 WebHID 授权与更多实体按键仍待回归**。
> 本文只写"已实现的事实 + 依据"，未验证的一律标注。

## 1. 架构

板子 = Waveshare RP2350-USB-A（RP2350A，`PICO_BOARD=pico2`）。

```
                 core1                                     core0
   ┌───────────────────────────────┐        ┌───────────────────────────────┐
   │ PIO 软 USB host（USB-A, GP12/13）│        │ 原生 USB device（USB-C）        │
   │  ├ 接口0 vendor 0xFF/0x5D      │        │  ├ 接口0 HID                   │
   │  │   EP1 IN 20B（XInput）      │        │  │   报告描述符 97B            │
   │  ├ HID 接口 1/2/3              │        │  │   输入 10/11B / Output 8B   │
   │  │   EP82/EP83/EP84 IN 64B     │        │  ├ 接口1 HID（Sensors, EP84）   │
   │  │   EP06 OUT 64B（接口 2）     │        │  ├ 接口2 HID（WebHID 配置）    │
   │  └ 命令 5a a5 …（开 test mode）│        │  └ 接口3/4 CDC（控制台）        │
   │ 合成状态 ──────────── g_fd ────┼───────▶│ 1 kHz 推 HID 报文              │
   └───────────────────────────────┘        └───────────────────────────────┘
```

双栈分工照官方示例 `Pico-PIO-USB/examples/host_hid_to_device_cdc`：**host 独占一个核、device 在另一个核**，各自把 `tuh_init`/`tud_init` 与自己的 task 放在同一个核上（USB IRQ 装在调用 init 的那个核）。

## 3. 必须照做的实现细节（每条都有代价换来）

1. **挂载前 DP/DM 强拉低 200 ms**（12 mA 驱动强度）——绕过板上 R13，否则接收器根本不挂载。
   依据：`refs/Flydigi5Pico/Flydigi5Pico.cpp` 的 `usb_force_reset_bus()`（作者标注"接收器可正常挂载的关键"）。
2. **TinyUSB 0.20 的 task 语义**：`tud_task()`/`tuh_task()` = `*_ext(UINT32_MAX, …)` = **等事件阻塞**。
   所以 core0 必须用 `tud_task_ext(0,false)`；core1 的 host 独占核，用阻塞版正好。
3. **按描述符匹配接口，不认接口号**：接口 0 = `class 0xFF && subclass 0x5D && (protocol 0x81||0x01)`；
   HID 类接口的所有中断 IN 端点都打开并独立轮询；本机实测扩展帧从 EP83 到达，EP82/EP84 也保持队列。
4. **命令走 EP06 中断 OUT 端点**（实机描述符把它挂在 HID 接口 2，64 字节）：启动顺序 = 4 条初始化握手 → `10 02 12` 状态查询 → 开 test mode；随后按抓包约每 500 ms 重发 `01 02 03`。
   Linux 参考驱动 `vader5pro-remap-driver` 走同一 HID 输出通道（`CONFIG_INTERFACE=1` 的 hidraw 写）。实机描述符同时声明 EP82、EP83、EP84 三个 HID IN，固件为每个端点保留独立队列；当前设备的 EP83 与 EP06 属于同一有效数据接口。
5. **扩展键有新鲜度窗口**（250 ms）：EF 帧断流时视为全部释放，避免背键粘住。
   EF 新鲜时优先提供摇杆、扳机、标准键、扩展键和 IMU；EF 过期时回退接口 0 的 XInput 标准输入。可选 `0x0008` 模式只允许更新的 XInput 摇杆轴覆盖 EF，扳机和按键仍取 EF。本机 Home 使用 EF byte14 bit3 的活动高电平（空闲 0x00、按下 0x08），EF 过期后兼容 XInput Guide bit10。接口 0 的 1 kHz 是主机轮询频率，不代表接收器持续产生 1 kHz 新报告；配置页分别显示 XInput、EF、USB 输出的实测速率。
6. **日志走自定义 CDC**，不启用 SDK stdio（`pico_enable_stdio_uart/usb` 都关）——SDK stdio_usb 会和自定义描述符打架。
7. **bring-up 诊断开关**：`BRINGUP_BOOTSEL_FALLBACK_MS=15000` —— 15 s 内没被主机挂上就自己退回 BOOTSEL，
   用来区分"固件跑挂了"（什么都不会发生）与"描述符不被接受"（自己跳回 BOOTSEL）。正式可用后删掉这条。
8. **震动回程**：设备 HID 接口声明 `0x01 OUT` 与 `0x81 IN` 两个中断端点；Output 报告为 8 字节 vendor 数据，
   固件接受 `00 08 00 LL RR 00 00 00`、`5a a5 12 06 LL RR` 及带 `03` 前导的格式；桥接固件默认在 250 ms 无刷新后向接收器发送零强度包停振。
9. **陀螺仪回程**：接口 1 是独立的 HID Sensors 接口，EP84 IN 每 1 ms 轮询一次，交替发送两个 6 字节报告：
   Report ID 1 = 角速度 XYZ（接收器原始 gyro 计数），Report ID 2 = 加速度 XYZ（4096 计数 = 1 g）。
   `flydigi_host_get()` 会从 EF 帧合并这 6 个字段；EF 帧过期时发送零值。

## 4. 参考工程 `Flydigi5Pico` 的两个坑（我们的增量）

1. **`usbh_app_driver_get_cb` 里 `*driver_count = 1` 但表里有 2 个驱动** → 第二个（接口 1）**从未注册**，
   所以它的扩展通道从来没真正打开过。我们写 `*driver_count = 2`。
2. 它的**接口 1 只发 SET_REPORT 试探负载**（`1c 00 74 07 66 08 dd ff ff 00`），没有按 protocol.md 发 `5a a5` 命令序列，
   所以拿不到 `5a a5 ef` 扩展帧（= 拿不到背键）。

## 5. 描述符陷阱（已踩，已修）

`TUD_CDC_DESCRIPTOR` **自带 8 字节 IAD**，`TUD_CDC_DESC_LEN = 8+9+5+5+4+5+7+9+7+7 = 66`。
第一版手工又写了一个 IAD 且 `CONFIG_TOTAL_LEN` 再 +8 → 描述符里出现**两个 IAD**，
刷进去后 macOS 侧**完全枚举不出来**。现由 `test/usb_desc_check.py` 覆盖此检查。

### Generic A/B 真机结果

初版 Generic 构建（`VID/PID=1209:0001`、Usage `0x01/0x05`）在 macOS IOHID 层枚举出 25 个按钮和 6 个轴，但 `GCController.controllers()` 保持 0。改用 Vader2Pro 三元组（`04B4:2412:0500`）后，同一 26 键报告布局收到 `GCControllerDidConnect`，暴露 38 个元素；当前板实际为“Vader 2 Pro，Connected”。因此“Usage 正确、按键/轴足够、VID/PID 非零、字符串存在”只能说明底层枚举条件满足，不能替代 Apple 模型匹配。

`1209:0001` 是 [pid.codes 私人测试 PID](https://pid.codes/1209/0001/)，可用于这块小板的本地验证；若要分发或制造设备，须先获得适用的独立 VID/PID，并同步更新固件和 WebHID 设备筛选。

`0x01/0x05` 是 HID Usage Tables 中的 Game Pad 用法，不是 Apple Game Controller 采纳保证，也不等于 USB-IF 对整机的认证。当前实测应分层解读：

| 身份 / 路径 | IOHID | Chrome Gamepad API | macOS `GCController` | 标准网页震动 |
|---|---|---|---|---|
| Generic `1209:0001`、26 键 | 可见 | 26 键，`mapping=""` | 0 台（等待连接后） | `vibrationActuator=false` |
| Vader2Pro `04B4:2412:0500`、20 键 | 可见 | 待本轮复测 | 已收到连接通知 | 待本轮复测 |
| 混合 Vader2Pro 身份、26 键 | 26 键可见 | 待实体复测 | 已连接，38 个元素；新增五键无独立 GC 名称 | 待复测 |

Apple 的[控制器发现说明](https://developer.apple.com/documentation/gamecontroller/discovering-game-controllers)只描述**受支持**控制器的 USB 连接，并未承诺任意 VID/PID 或自制 HID Game Pad 都进入 `GCController`。WebKit 的 [macOS IOHID provider](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/gamepad/mac/HIDGamepadProvider.mm) 单独匹配 Game Pad usage；其 [Game Controller provider](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/gamepad/cocoa/GameControllerGamepadProvider.mm) 消费框架已发现的控制器。前者的 `playEffect` 明确返回不支持。因此网页能看到 Generic 输入，也不能据此推断原生游戏或标准 Gamepad 震动可用。iOS/iPadOS 尚无目标设备实测，USB 枚举、游戏输入、额外键和震动都须分别验证，不能从 macOS 结果外推。

Apple 的 [iPhone 手柄说明](https://support.apple.com/guide/iphone/connect-a-game-controller-iph9d38dd45f/ios)同样限定为“兼容的”有线手柄；它没有承诺任意自制 HID Game Pad 的游戏兼容性。2026-09-30 再次在当前 Generic 固件上读回 `flags=0x0001`、26 键浏览器顺序和完整 Feature 响应；接收器在线、电量约 60%、EF 帧持续增长，但静置期间板内输入年龄样本数仍为 0。`GCController.controllers()` 等待 5 秒后仍为 0；Mac 处于锁屏状态，SCUF 新身份的 USB 授权实验尚不能进行。配置页的震动测试状态现按设备最后确认接受的左右增益和看门狗计算，并覆盖未应用表单及应用失败的情况；这只是状态显示修正，没有改动当前已刷固件的马达时序。真机再次发送 `180/180` Feature 测试后，接收器震动发送计数从 1 增至 3（启动与自动停振各一包），失败计数为 0；马达体感仍需人工确认。

`GENERIC_APPLE_IDENTITY=ON` 是独立实验构建，要求同时设置 `GENERIC_GAMEPAD=ON`。它保留 26 按钮的 11 字节 Game Pad 报告，但使用 Vader2Pro 的 `04B4:2412:0500` 身份。第一轮浏览器顺序构建在 macOS 收到 `GCControllerDidConnect`，出现 38 个 GC 元素，IOHID 仍列出 26 个按钮；Apple 模型按按钮类别中的位置取值，因此这轮默认顺序会错位。第二轮将前 20 位改回 Apple 模型顺序，C/Z/LM/RM/O 放在 20–24 位，主机侧 65 项映射检查通过；刷写后再次收到 GC 连接通知、38 个元素和 26 个 IOHID 按钮，Feature 读回默认映射 `M1–M4=14–17`、`Home=19`、额外键 `20–24`。Apple 模型的 38 个 GC 元素未列出额外五键；它们目前只可确认在 IOHID 的 26 按钮表中。GC 输入值及浏览器完整行为仍待实体按键回归。

为避免把纯 Generic 构建误刷到 macOS 原生使用场景，`firmware/rp2350/CMakeLists.txt` 新增 `APPLE_COMPATIBLE_PROFILE=ON`。该目标自动组合 `GENERIC_GAMEPAD` 与 `GENERIC_APPLE_IDENTITY`，并拒绝 PID、Stadia、SCUF 实验选项。2026-09-30 用该目标重新配置并编译通过，`usb_desc_check.py --generic-apple` 验证 `04B4:2412:0500`、26 键报告、传感器和 WebHID 三个接口；USB 注册表显示 `Vader 2 Pro，Connected`，`gc_watch` 收到一个 `GCControllerDidConnect` 和 38 个元素。

同日新增 `APPLE_BATTERY_PROBE=ON`，在相同 Apple 身份下附加 120 字节 HID 报告描述符中的 Battery Strength Report ID 3；`usb_desc_check.py --generic-apple --apple-battery`、默认/Apple/探针固件编译均通过。随后实刷验证：IOHID 能解析 `0x84/0x20`，但游戏输入探针只收到 Report ID 3，`USB reports=0`，所以该方案会破坏无 Report ID 的游戏报告，`GCController.battery` 仍为 `nil`；已恢复稳定镜像，不能继续使用。

系统侧补充证据：`defaults read com.apple.GameController` 当前已持久化 `Vader 2 Pro` 控制器记录，包含 A/B/X/Y、肩键、扳机、方向键、摇杆和四个背键的元素名称；该记录的 `supportsHaptics=0`，且没有电量字段。因而“系统设置页面没有显示”不能解释为设备未被 `gamecontrollerd` 收录，需先关闭并重新打开设置页或重新插拔后再观察 UI；原生触觉/电量则是独立能力缺口。

随后先用 `picotool save -a -v /tmp/flydigi-pre-apple-profile-20260930.uf2` 做整片备份，再刷入 `rp2350/build-apple-compatible/flydigi_bridge.uf2`；写入和校验均返回 `OK`。重启后的 USB/GCController 结果保持不变，`gc_watch` 仍看到 Vader 2 Pro、26 个 IOHID 按钮和 38 个 GC 元素。刷后 WebHID Feature 读回配置 token 支持、26 键映射、gyro/accel Report ID 1/2 非零样本；等待接收器完成周期性 device-info 查询后，CDC 显示 `battery_valid=1 level=100 updates>0`，WebHID `GET_INFO` 也返回电量 100%。`--rumble-timing` 实测启动与自动停振 `sent 1 -> 3`，配置往返恢复 PASS。第一次刚重启即读取时出现的“电量未知”只是查询尚未完成，不是有效读数被覆盖。

实验构建从易失默认映射启动，既不读取普通 Generic Flash 映射，也拒绝 Save/Reset 写入同一 Flash 区。真机 Save Feature 返回状态 `2`；刷回 Generic 后读回原 `flags=0x0001` 和完整浏览器顺序映射。网页依据 `GET_INFO[14]=1` 显示 Apple 顺序槽位并禁用保存。实验固件已刷回原 Generic；构建命令可用 `-DGENERIC_GAMEPAD=ON -DGENERIC_APPLE_IDENTITY=ON`，离线描述符检查用 `usb_desc_check.py --generic-apple`。

另一个独立候选是本机 Apple 模型库的 `Corsair/scuff-omega/Default.plist`。其 `IOPropertyMatch` 为 `1B1C:3A28`，模型把 Button 21–24 作为四个 `BUTTON_M*`，Button 25–29 作为五个 `BUTTON_G*`；能为 Vader 的 M1–M4 与 C/Z/LM/RM/O 提供九个分别命名的 GC 元素。实验选项 `-DGENERIC_GAMEPAD=ON -DCORSAIR_APPLE_IDENTITY=ON` 输出 29 按钮、11 字节报告，摇杆轴为 X/Y/Z/Rz，扳机为 Simulation Controls 0xC4/0xC5。该变体也隔离普通 Generic Flash 映射、拒绝 Save/Reset；网页 `GET_INFO[14]=2` 对应其按钮槽位。65 项主机映射检查、配置测试、112 字节描述符检查及固件构建均通过。`firmware/scuf_model_conform.py` 另以 plist 解析验证 29 条模型谓词唯一命中，以及九个额外键的名称和值来源。

第一次把 SCUF 候选刷入小板时，Mac 处于锁屏；USB 注册表短暂出现 `1B1C:3A28` 的未注册设备节点，没有接口、GC 连接或 WebHID 配置接口。15 秒后固件的 bring-up 保护退回 BOOTSEL。[Apple 的配件授权说明](https://support.apple.com/en-gb/102282)指出 Apple Silicon 笔记本的新 USB 配件可能需要在解锁后批准。**新身份的系统授权状态或其他身份匹配条件尚未确定**，不能说 Apple 已采纳这个模型。已刷回 Generic，确认配置仍为 `flags=0x0001` 且浏览器顺序映射完整。SCUF 实验构建现单独给出 60 秒授权窗口；下一次应在解锁、处理系统 USB 授权提示后重试枚举，再用实体按键验证 GC 元素值。
