| # | 风险 / 未知 | 级别 | 怎么验证（成本） | 失败退路 |

| R5 | **PIO-USB 稳定性/抖动**：软件 PHY 下 1kHz 轮询 + 双端点 | 🟡 | 板内计数器统计 IN 端点超时/重试次数，连续跑 30 分钟 | 换双 USB 控制器 MCU（见 04 §3 备选） |
| R6 | **枚举与热插拔竞态**：接收器上电慢、Mac 睡眠唤醒后 device 侧重新枚举 | 🟡 | 反复拔插 20 次 + 睡眠唤醒 5 次，记录失败率 | 上电加延时 + 物理总线复位（先例已证明有效），device 侧重挂后重置状态机 |

## 尚未验证、但文档里已按"待验证"标注的假设清单

1. 19 字节/17 字节/18 字节三处报告长度说法不一致（docs/03 §2）→ R1。
2. 苹果 dext 的 GIP 会话是否含 security 握手（docs/03 §5）→ R2。
3. 飞智接口 1 的 test mode 命令在**接收器**上是否与在手柄上有相同行为（协议文档来自 2.4G 接收器实测，但 test mode 只在先行项目里对本机有线/接收器两种路径混合使用过）→ R4。
4. 有线直连（USB-C）模式的 VID/PID 与接口布局（udev 规则里出现 `04b4` 可能来自 DInput，未确认）→ Phase 0 P0-2。
5. iPad 上拨片是否在所有 App 中映射到预期元素（已有一次“可用”用户实测，但没有保存机型、iPadOS、App 和逐键日志）→ 建立 R16 矩阵。

## 关键判断（写在最后，避免被前面的细节淹没）

- **这个项目的可行性分界线不在"能不能读飞智"**（读协议已被两个参考仓库和 Flydigi5Pico 证明），**而在"能不能让 macOS 采纳我们伪装的 Elite"**。
- 因此**最先做的三件事应该是**：Phase 0 实测 → 反汇编本机 dext/插件弄清主机侧 GIP 脚本 → 复刻 360 桥验证骨架。iPad 目前已有成功使用记录，但 R11/R16/R17 的供电、长期稳定性和副作用仍需单独验收；**任何写 Elite 固件的工作都应排在这三件之后**。
