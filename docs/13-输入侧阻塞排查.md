# 13 · 输入侧阻塞排查（core1 停在 tuh_rhport_init）

> 状态：**已解除（2026-09-30）**。本文保留早期阻塞证据；当前固件已经能够从
> `37d7:2401` 接收器收到活动 EF/XInput 输入，并桥接到 USB HID。

## 最新真机结论（2026-09-30）

- 活动触发探针已在同步操作窗口内检测到输入变化：EF 约 **94.7 Hz**，XInput
  约 **309.6 Hz**，USB 游戏 HID 约 **974.5 Hz**，板内输入变化约 **32.5 Hz**。
- 输入年龄样本为 **261**，最近值约 **0.20 ms**，窗口最大约 **7.20 ms**；这
  是接收器新帧到桥接状态的年龄，不把 1 kHz USB 保活误报成 1 kHz 接收器输入。
- 原生输出回归捕获到 A 独立按下/释放；同一轮用户操作中 M1、M2 两个输出槽位
  同时变化。由于该轮未同步保存 EF 原始字节 13，不能据此判定是实体同时按键还是
  接收器位。修改 M1/M2 位序前必须再做单键原始 EF 采样。
- 活动后 `GCControllerDidConnect` 收到通知，`GCController.controllers()` 为 1，
  控制器名为 `Vader 2 Pro`，包含 38 个元素；IOKit 看到 26 个按钮和 6 个轴。
- 当前 Apple 兼容身份的标准 GameController 对象仍不提供 `haptics` 和 `battery`；
  WebHID 配置接口可读电量、传感器和震动状态。`--rumble-timing` 实测启动/停振
  计数为 `1 -> 3`，看门狗 250 ms，配置回读恢复通过。

因此早期“接收器全 NAK、没有输入链路”的结论只适用于手柄未在线或静止窗口；在
手柄保持 2.4G 配对并实际操作时，链路已经恢复，不应再修改 USB 映射来解决该旧症状。

## 症状（可复现）

固件跑起来后读控制台（`i`）：

```
core1 alive=1 stage=2 ticks=0 tuh_ret=0 | mounts=0 umounts=0 xi=0 ex=0
recv=0 vid=0000 pid=0000 itf(x=0 e=0) ...
xr=0 er=0 ef=0 cmd=0
```

- `stage=2` = `tuh_configure(1,…)` 已返回（写 `s_core1_stage=2`），`tuh_init(1)` 未返回（`stage=3` 永不出现）
- `alive=1` = core1 进过 `core1_host()`
- `ticks=0` = core1 从未进主循环
- **设备侧完全正常**：Mac 认到 `04b4:2412`，HID 元素齐全（含 4 个背键），`sent` 持续增长

反汇编佐证（`build_dbg`）：

```
10000206: bl tuh_configure        ← 返回
10000210: str r3, [r6, #0]        ← s_core1_stage = 2   ✔ 生效
10000216: bl tuh_rhport_init      ← 进入 host 栈初始化   ✘ 不返回
10000220: str r3, [r6, #0]        ← s_core1_stage = 3   （永不执行）
```

## 对照实验（官方示例）

`~/pico/Pico-PIO-USB/examples/host_hid_to_device_cdc` 编到 `PICO_BOARD=pico2`
（平台 `rp2350-arm-s`，与我们的固件相同）→ 烧进去后 **CDC 一个字节都不输出、敲键无反应**。

⇒ **不是我们固件的配置问题；官方示例在这块板子上同样停住**。

## 已排除的假设（每条都有实验）

| 假设 | 排除方式 | 结果 |
|---|---|---|
| 重复 IAD 导致枚举失败 | 修改描述符 + `test/usb_desc_check.py` | 已修复，与本问题无关（设备侧本来就好） |
| core1 与 core0 争初始化顺序 | 把 host 初始化挪到 core0（延迟 2.5 s） | **core0 上同样停住** ⇒ 与核无关 |
| `alarm_pool_create` 资源冲突 | core0 预建报警池并传入 `pio_cfg.alarm_pool` | 池非 NULL，症状不变 |
| DMA 通道冲突 | 显式 `tx_ch` | 症状不变 |
| 编译期宏缺失（`PIO_USB_USE_TINYUSB` 等） | 对照官方示例的宏集 | 官方示例同样失败 |
| 两份 HCD 实现冲突 | `nm`/`objdump` 确认只有 PIO 版 `hcd_init` 被链入 | 排除 |
| 库内部某段挂死 | 在库源码插 8 个位置标记（`-dbg` 影子副本） | `dbg_pio` 读回全 0，但符号唯一、库确实在写 ⇒ **core1 未走到该处** |
| core1 栈溢出（默认 2 KB） | 调到 3 KB 并验证 | 症状完全不变 ⇒ 排除 |
| `PICO_RP2350` 条件编译（E9 errata 变通） | 读 `pio_usb_ll.h:144` | 该变通在读取行状态时执行，与初始化无关 |
| `usb_force_reset_bus()` 留下异常引脚状态 | 加 `SKIP_USB_FORCE_RESET` 跳过 | 症状不变 ⇒ 排除 |
| 我们的类驱动 `init()` 阻塞 | 读源码：两个驱动 `.init` 均为 `NULL` | 排除 |
| `osal_queue_create` 阻塞 | 读 `osal_pico.h`：纯内存操作 | 排除 |
| `tuh_configure` 阻塞 | 反汇编：`hcd_configure` 只做 memcpy；`stage=2` 已生效 | 排除 |

## 结论与下一步

`tuh_rhport_init(1)` ⇒ `hcd_init` ⇒ `pio_usb_host_init` 这条链上，**core1 停住且不返回**。
静态排查已穷尽（每个调用点都读过源码），剩下必须靠**运行时 PC**：

**下一步探针**：在 core1 上用一个独立硬件报警器周期性把该核的 `PC`/`SP` 写进 RAM，
core0 读出来反查符号，直接看它停在库内哪个函数。

## 备选路线（若探针确认是库/硬件不兼容）

### A. 换 USB host 实现
- **官方 PIO 示例在不同板子上验**（隔离"板子"与"库"）
- **ESP32-S3 / ESP32-P4（内置 USB-OTG host）** 作为输入侧主控，避开 PIO 软 USB：RP2350 只做 device
- **RP2350 用原生 USB 控制器做 host**（需硬件上把 USB-A 接到原生 USB 引脚）

### B. 换输入侧数据源
- **飞智手柄蓝牙（BLE）路线**：`refs/vader5pro-remap-driver` 与 macOS 侧都表明 BLE 下背键 index 明确
  （`m1..m4 = 22/20/21/17`），不必碰 2.4G 的专有 test-mode 协议
- 代价：BLE 不能同时走 2.4G 低延迟，且需要自己实现 BLE HID host

### C. 降低目标
- 只做**标准键 + 摇杆**的桥（接口 0 的 20 字节报文已完整逆向），放弃 M1–M4

## 附：设备侧（输出）已闭环的结论

这部分**已实测通过**，与输入侧阻塞无关，可直接复用：

- macOS 认成 `Flydigi Vader 2 Pro`（`GCController` 层面 `vendor=Vader 2 Pro`）
- `physicalInputProfile.elements` 共 **38** 个，其中背键为 4 个独立元素：
  `Back Left Button 0 / Back Left Button 1 / Back Right Button 0 / Back Right Button 1`
- IOKit 直查：按钮 usage = **1..20**，轴 usage = **4, 48..53**，hat = 1
- 官方模型 `MobileUSBWithBackButtons.plist`（`b1e50bde…` 那份）里的定义：

| Identifier | LocalizedNameKey | Alias（元素名） | Predicate |
|---|---|---|---|
| `button.m1` | `BUTTON_M1` | Back Right Button 0 | `UsageType==1 && UsageTypeIndex==14` |
| `button.m2` | `BUTTON_M2` | Back Left Button 0 | `UsageTypeIndex==15` |
| `button.m3` | `BUTTON_M3` | Back Right Button 1 | `UsageTypeIndex==16` |
| `button.m4` | `BUTTON_M4` | Back Left Button 1 | `UsageTypeIndex==17` |

`UsageTypeIndex` 是从 0 起的按钮类内序号 ⇒ 14..17 对应第 15..18 个按钮元素，
与固件把 M1..M4 放在 usage 15/16/17/18 完全对齐。

**待补**：M1..M4 与逻辑名 `m1..m4` 的物理对应关系（需按实键确认），
以及模型里 `PressedValueSource = 45/43/46/44` 语义未定（标准键为 4/5/6/22 等小值）。
