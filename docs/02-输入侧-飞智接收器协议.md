## 1. 设备身份与接口布局

| 项 | 值 | 证据 |
|---|---|---|
| 2.4G 接收器 VID/PID | `0x37d7` / `0x2401` | udev 规则、内核驱动补丁 |
| 有线/其他模式 | udev 规则另有一条 `idVendor=04b4`（Cypress，注释写 "DInput mode if applicable"） | `install/99-vader5.rules` |
| 接口 0 | Vendor Class `0xFF` / SubClass `0x5D`；EP1 IN 20B，EP5 OUT 8B | protocol.md |
| 接口 1 | HID；EP2 IN 32B，EP6 OUT 32B —— **扩展输入 + 配置命令** | protocol.md |
| 接口 2 | HID；EP2 IN 32B（未用） | protocol.md |
| 接口 3 | HID；EP4 IN 64B（键盘模式） | protocol.md |

关键点：**接收器不是标准 HID 手柄**。它的"手柄主通道"是接口 0 的 vendor 类 XInput，通用 HID 驱动会忽略它——这正是 macOS 认出设备却收不到输入的原因。
（Flydigi5Pico 的 Host 匹配逻辑因此不盯 VID/PID，只认 `SubClass == 0x5D && (Protocol == 0x81 || 0x01)`。）

## 2. 接口 0 · 标准输入报告（20 字节）

和 Xbox 360 XInput 的 20 字节布局一致：

| 偏移 | 含义 |
|---|---|
| 0 | Report ID = `0x00` |
| 1 | Subtype = `0x14`（2.4G） |
| 2–3 | 按键（uint16 LE：DPad/Start/Back/L3/R3/LB/RB/Guide/ABXY） |
| 4 / 5 | LT / RT（0–255） |
| 6–13 | 左摇杆 X/Y、右摇杆 X/Y（int16 LE） |
| 14–19 | 保留 |

按钮位（Flydigi5Pico 实测映射，bit0 = DPad Up … bit15 = Y）：
`bit0..3 = DPad U/D/L/R`，`bit4 = Start`，`bit5 = Back`，`bit6 = L3`，`bit7 = R3`，`bit8 = LB`，`bit9 = RB`，`bit10 = Guide`，`bit12..15 = A/B/X/Y`。
**这条通道没有 M1–M4 / C / Z / LM / RM，也没有陀螺仪。**

## 3. 接口 1 · 扩展输入 + IMU（32 字节，需先开 test mode）

报文以魔数 `5a a5 ef` 开头；字段依次为：四轴 int16（左 X/Y、右 X/Y）、按钮 1（DPad+A/B/Select/X）、按钮 2（Y/Start/LB/RB/L3/R3）、**扩展按键（C/Z/M1–M4/LM/RM）**、扩展按键 2（O/Home）、LT、RT、陀螺 XYZ、加速度 XYZ。EF 帧 `byte[11]` 的 D-pad 位序是 **U/R/D/L**（bit0/1/2/3）；接口 0 的 XInput 报告仍按 U/D/L/R 解析后再归一化。完整位表见参考仓库 `docs/protocol.md`。

开启方式（发往接口 1 的 32 字节命令，魔数 `5a a5`）：

```
5a a5 11 07 ff 01 ff ff ff 15 00 ...   # 开 test mode（扩展输入 + IMU）
5a a5 11 07 ff 00 ff ff ff 14 00 ...   # 关
```

初始化握手（连接后必须做，否则无数据）：

```
5a a5 01 02 03   # device info
5a a5 a1 02 a3   # MAC/serial
5a a5 02 02 04   # config read
5a a5 04 02 06   # config data
```

其他有用命令：`5a a5 a2 03 XX YY`（切 profile 0–3）、`5a a5 12 06 LL RR`（test mode 震动）。

## 4. 震动（Host → 接收器）

- 接口 0 / EP5 OUT，8 字节，Xbox 360 格式：`00 08 00 LL RR 00 00 00`
  （Flydigi5Pico 实测：`txbuf[3]=左马达`，`txbuf[4]=右马达`）
- 或经 test mode：`5a a5 12 06 LL RR ...`

## 5. SDL 的独立佐证（值得抄的地方）

`SDL_hidapi_flydigi.c` 里可确认：
- 新接收器（V2，含 Vader/Apex 6）**只暴露一个自定义 HID 接口**，且"接受任何接口号"；老款用接口 2；
- 报文首字节是 `0x5A` 魔数，否则整包要去掉 report ID 再看；
- 扩展按键解析位置：`data[13]` 的 bit0/bit1/bit2(M1)/bit6/bit7、`data[14]` 的 bit0……（与 §3 的 32 字节布局一致，偏移差来自有无 report ID）；
- SDL 有 `SDL_GAMEPAD_BUTTON_FLYDIGI_M1` 等自定义按钮枚举，说明这些键在位图上确有独立定义。

## 6. 对本项目的直接结论

1. 想要 M1–M4 → **必须读接口 1 并开 test mode**（只读接口 0 的 360 通道拿不到背键）。
2. 需要验证的副作用：**开 test mode 会不会改变接口 0 的 XInput 数据流/频率**（未验证，见 06 风险 R4）。
3. 有线直连（USB-C）与接收器在当前文献里被当作同一套 XInput 接口处理；如果用有线，需先实测其 VID/PID 与接口布局是否与接收器一致（大概率不同 PID）。

## 7. 实测验证（2026-09-29 · 真机接收器 + 板子 stage-2 固件）

### 7.1 背键位图（定案，双源一致）
参考实现 `Chillsmeit/vader5pro-remap-driver/docs/protocol.md`（已拉取原文，存 `~/.hermes/cache/scratch/proto.md`）给出扩展输入帧（32 B，魔数 `5a a5 ef`）的完整偏移，其中：

```
[13] 扩展按键:  bit0=C  bit1=Z  bit2=M1  bit3=M2  bit4=M3  bit5=M4  bit6=LM  bit7=RM
[14] 扩展按键2: bit0=O  bit3=Home
```

**与真机帧逐字段交叉验证通过**。开机瞬间抓到的唯一一帧：
```
5a a5 ef | 09 00 | 08 00 | e5 ff | e2 ff | 00 | 00 | 00 | 08 | 00 | 00 | f4 ff | a1 00 | 34 01 | 63 ff | ef 00 | a7 11 | 00 00 | 9f
```
- LX=9, LY=8, RX=−27, RY=−30（与固件解码出的 9 / −8 / −27 / 30 一致，仅符号约定不同）
- `[11]=[12]=[13]=0x00`：无按钮、**无背键**（当时未按）✓
- `[11..16]` 按钮/扳机全 0、`[17..22]` 陀螺有值、**加速度 Z = 0x11a7 = 4519 ≈ 1.10 g**（静止时理论 1g）✓
- `[31] = 0x9f`：EF 尾校验字节。两份早期样本和 2026-09-30 连续取到的 99 个不同 EF 帧都满足 `byte[31] = (1 + sum(byte[0..30])) & 0xff`。固件据此拒绝校验不符的 EF 帧，并在 CDC 状态中记录 `ef_bad`；其他类型回复帧不能套用这条 EF 规则。

⇒ **M1–M4 的位就是 `byte[13]` 的 bit2/3/4/5。**

**真机 Home 电平已确认**：静止空闲帧 `[14] = 0x00`，按住物理 Xbox/Home 键时变为 `[14] = 0x08`，松开后恢复 `0x00`。同步采样中接口 0 的 XInput bit10 也从 `0` 变为 `1`，因此 bit3 是本接收器的活动高电平 Home；固件在 EF 新鲜时采用此位，EF 断流后才用 XInput bit10，避免稀疏 XInput 包延迟 Home 松开。[Vader 5 Linux 实现](https://github.com/BANANASJIM/flydigi-vader5/blob/5d8671db056f786d0c708f5df30482167ef6e6ff/src/uinput.cpp#L210-L222)同样按 EF 位的变化发出按下和松开；[MiSTer xpad 实现](https://github.com/MiSTer-devel/Linux-Kernel_MiSTer/blob/794ad00d1be5ae272c508c0663e5665656f3bb7a/drivers/input/joystick/xpad.c#L1309-L1319)启用扩展流后跳过标准 XInput 输入。`byte[14]` 的其余位仍未单独实测。

### 7.2 板子固件为什么拿不到背键（根因）
实测第三方固件（板子上刷的 `RP2350 Pad Bridge (stage 2)`，非本机编译）：

| 观测 | 值 | 含义 |
|---|---|---|
| `dongle: tx=0` | 从枚举到现在**写入次数 0** | 初始化握手与 test mode 命令**一条都没发** |
| 接口 `5a a5` 通道（usage `FFA0/0001`，32B EP） | 92 次/秒，`last_len=32` | 数据在流，但全是 `5a a5 01 01 00 82 …` 这一固定帧 |
| `state` 解码值 | 157 秒内 299 个样本**完全相同** | 没有一帧 `5a a5 ef` 输入帧到达 |
| 唯一一帧 `5a a5 ef` | 开机瞬间 1 次 | 之后从未再现 |

⇒ 与 §3 一致：接口 1 的扩展输入（含背键）**必须先由主机发命令开 test mode**，而该固件只读不写（`tx=0`），且连 §3 的初始化握手都没做。**背键拿不到是固件输入路径未完成，不是硬件/接线问题。**

### 7.3 待办（固件侧）
1. 连接后依次发：`5a a5 01 02 03` → `5a a5 a1 02 a3` → `5a a5 02 02 04`（§3 握手），再发 `5a a5 11 07 ff 01 ff ff ff 15 00…` 开 test mode。
2. 读接口 1 的 32 B 帧，按 `byte[13]` 取 M1–M4。
3. 需验证的副作用（原文 §6.2 未解）：开 test mode 是否改变接口 0（XInput 20B）的流速/内容。
4. 另需处理：该固件的 `tx` 通道（EP6 OUT 32B）在 macOS 侧对应的写入口——接收器直连 Mac 时的实验（`firmware/probe/rx_poke.swift`）可先行验证握手命令是否真能让 `5a a5 ef` 帧流起来。

### 7.4 XInput 保留位防护

接口 0 的按钮字按协议只使用 bit0..10 和 bit12..15，bit11 没有定义。一次
实体按键采样曾收到 `raw=ff00`，该包同时置位了保留 bit11、ABXY、LB/RB 和
Guide；若直接合并，会伪造“几乎所有按键同时按下”。桥接固件现在保留该原始包
供 `x` 诊断，但在合并前丢弃并在 CDC 状态的 `xi_bad` 计数中记录。合法 XInput
按键位和 EF 扩展帧映射不受该过滤影响。
