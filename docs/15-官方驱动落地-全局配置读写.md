# 15 - 官方驱动落地：全局配置读写（0xA3 读 / 0xA0 写）

> 2026-10-18。来源：官方"空间站"网页驱动的 Node 模块（解读记录保存在独立私有研究项目，官方代码与资产不进入本仓库）。本文只写**已在本板 + 本接收器真机验证**的事实；未验证项明确标注。

## 1. 结论速览

- 官方驱动存在一条**设备端全局配置**读写通道：读 = 命令 `0xA3` 分块读 RAM1，取 `slice(2,82)` 的 80 字节 blob；写 = 命令 `0xA0`（`setDeviceConfig` 字段写），是官方代码中**唯一**的配置写路径（`0xA4/0x14/0x17` 均为死代码或旧版本）。
- 本板真机验证（2026-10-18）：
  - **"1K 回报率"获官方实证**：设备自身配置值 `usbReturnRateHz = 1000`（此前只有营销口径与 acquire 档 EF ≈ 700+ Hz 的旁证）；
  - 睡眠定时器读得 `15 分钟`（出厂值），经 `0xA0/32` 写入 `0 = 永不`，**回读确认 15 → 0**（此前 `0x17` 的旧写路径静默无效）；
  - `0xA0` 应答布局在现场得到行为证实：写睡眠 → `status=0 fieldId=32`；写回报率 → `status=0 fieldId=33`。
- 固件据此新增：开机自动读取（`[CFG]` 状态行）、**睡眠自愈**（任何一次成功读取发现睡眠 ≠ 0 时自动写回"永不"，每挂载最多一次）、WebHID 命令 `0x08/0x09/0x0A`、控制台 `g`/`S`/`1/2/4/8` 走官方通道。

## 2. 读路径：0xA3 分块读

- 帧模板：`5A A5 A3 06 00 01 CC 10 CS`（`CC`=块号，`10`=每块 16B，`CS = Σ[2..n-1] & 0xFF`）。
- 固件状态机连读 6 块（96B ≥ 80B 所需），每块等待应答后再发下一块；2 秒超时计一次 `err`。
- 取应答数据 `[2..82)` 的 80B blob，解析字段（官方语义，固件 `flydigi_gcfg_parse`）：

| 偏移 | 字段 | 语义 |
|---|---|---|
| 3 | `sleepTime` | 睡眠分钟数；0 = 永不 |
| 7..38 | 名称 | UTF-8，非可见字符替换为 `.` |
| 41 | `usbReturnRateHz` | u16LE；`{500/250/125}` 有效，其它值视为 1000 |
| 43 | `jsResolution` | 摇杆分辨率（8..12） |
| 47 | `allowThirdparty` | 1 = 允许第三方接管（acquire 生效的前提） |

真机读回（2026-10-18，接收器 + 手柄在线）：`rate=1000Hz sleep_min=15→0 thirdparty=1 jsres=10`。

## 3. 写路径：0xA0 字段写

- 帧模板（官方 Node 模块实测格式，经本板复验）：
  - 睡眠：`5A A5 A0 04 20 VV CS`（`VV` = 分钟数，0 = 永不）
  - 回报率：`5A A5 A0 05 21 LL HH CS`（u16LE Hz）
  - `CS = Σ[2..n-1] & 0xFF`
- fieldId 全表见研究项目笔记；本固件只使用 `32 = sleepTime`、`33 = usbReturnRateHz`（`34/37/38` 保留）。
- **应答布局**（行为证实）：`5A A5 A0 pkgCount pkgIndex status fieldId CS`，即 `status@[5]`、`fieldId@[6]`。真机序列（CDC `i` 的 `[A0]` 行）：
  - 写睡眠=永不 → `[A0] replies=1 status=0 field=32`
  - 写回报率=1000 → `[A0] replies=2 status=0 field=33`
- 回报率写入在本设备上为幂等操作（设备已是 1000Hz），不能单独证明写后速率变化；睡眠写有 15→0 回读闭环。

## 4. 睡眠自愈（固件新增）

背景：15 分钟睡眠定时器是接收器侧掉线循环的已知来源；旧 `0x17` 写路径静默无效。

实现：**任何一次成功的全局配置读取**（开机自动 / 控制台 `g` / 网页读取）若解析出 `sleep_minutes != 0`，固件自动排队一次 `0xA0/32` 写入 0；**每挂载最多触发一次**（护栏，避免写入失败时的重试风暴）。

真机行为矩阵（2026-10-18 实测）：

| 场景 | 观察 |
|---|---|
| 写 15 → 随后任意读取 | 自动写回 0；`[A0]` 出现两条 `field=32` ACK（写入 + 自愈） |
| 同一挂载再写 15 | 护栏生效：只有写入 ACK，不再自愈；读取保持 15 |
| 重启板子（新挂载） | 开机自动读取到 15 → 自动写 ACK（`replies=1 field=32 status=0`）→ 新读取 `sleep=0` |

## 5. 固件与控制台

- 开机自动读一次全局配置（`s_gcfg_auto_done`），`[CFG]` 状态行无需按键即可填充。
- 写 API 泛化：`flydigi_host_request_sleep_minutes(uint8_t)`、`flydigi_host_request_report_rate_hz(uint16_t)`（替换原 `sleep_never`/`rate value` 版本）。
- 控制台命令（CDC 115200）：
  - `g` = 读一次全局配置（约 0.5 s）
  - `S` = 写睡眠=永不（`0xA0/32/0`）；`1/2/4/8` = 写回报率 1000/500/250/125 Hz（`0xA0/33` u16LE）
  - `i` 状态行新增 `[CFG]`（rate/sleep/thirdparty/jsres/name/reads/err）与 `[A0]`（replies/status/field）；`[DEV]` 的 `hw status`（cmd 03）请求与解析已随内部重构移除（设备不应答），`[DEV]` 不再含 hw 字段。
- **CDC 缓冲区升级**：`CFG_TUD_CDC_TX_BUFSIZE` 512 → 4096。2 秒心跳状态一次约 900B 突发，512 会在尾部丢行（曾系统性丢失 `[A0]/[AGE]/[POWER]/[OPEN]`）。

## 6. WebHID 接口（命令 0x10 / 响应 0x11）

| 命令 | 载荷 | 响应布局（status[0]、版本[1] 之后） |
|---|---|---|
| `0x08 GET_GCFG` | — | `[2..3] rate u16LE；[4] sleep；[5] flags（bit0 有效 / bit1 第三方）；[6] jsres；[7..10] reads u32；[11..14] errors u32；[15..30] name 16B；[31] 恒 1（本次已排队新读取）；[32..35] a0_replies u32；[36] a0_status；[37] a0_field` |
| `0x09 SET_SLEEP` | `[1]=分钟（0=永不）` | `[2]=回显` |
| `0x0A SET_RATE` | `[1..2]=Hz u16LE` | `[2..3]=回显` |

- `GET_GCFG` 语义：**返回缓存 + 排队一次新读取**（若读取已在进行则忽略本次排队——防重入；旧实现在读取中重启读取会把在途分块应答判为乱序而中断，2026-10-18 修复，见 `docs/16`）。回读同步 = 轮询直到 `reads` 计数超过基线（页面试写后自动执行，600ms × 最多 8 次）。
- 配置页新增「接收器全局配置」面板（读取 / 写睡眠 / 写回报率 / 最近写入结果），`node web/bridge-config.test.js` 覆盖解析、编码、轮询与禁用态。

## 7. 探针工具

`firmware/probe/hid_config_probe.swift` 新增：

```sh
swift firmware/probe/hid_config_probe.swift --apple --gcfg              # 只读（触发新读取并解析）
swift firmware/probe/hid_config_probe.swift --apple --set-sleep=15 --gcfg  # 写睡眠后回读
swift firmware/probe/hid_config_probe.swift --apple --set-rate=1000 --gcfg
```

## 8. 未覆盖 / 边界

- `0xA0` 应答的原始字节未抓包核对（`status/fieldId` 解析由真机行为证实）；多帧应答（`pkgCount>1`）未测。
- `jsResolution` 写路径（fieldId 34）已实现：控制台 `j`（8..12）+ WebHID `0x0C SET_FIELD`（白名单含 34），复用 0xA0 通道（见 `docs/16`）。
- 睡眠自愈只写"永不"，不提供自动恢复原值；写入失败的挂载不会重试（护栏设计取舍）。
- 回报率写入对 EF 高帧率流的影响未知（本设备已在 1000Hz，无可观测空间）；acquire 档 EF ≈ 700 Hz 与 `usbReturnRateHz` 的关系仍需多档写入对照实验。
- **已知接收器异常（2026-10-18 发现）**：接收器偶发把 XInput 报文字节"拼接"进 EF 帧——错位 2 字节的拼接帧被 EF 校验拒绝（`ef_bad` 的 0.6% 稳态来源即此，非随机误码）；对齐的拼接帧可通过校验，理论上可产生单帧（~1ms）幽灵按键。事件环可见其爆发（`b=0c/0b ext=22/08` 等固定组合 @100Hz）。待办：可加"不可能组合 + XInput 摩擦"防御。详见按键底层码核对记录（研究项目笔记 08）。
