# 04 方案对比、推荐路线与硬件选型

> 本文记录早期 GIP/Elite 方案比较，推荐结论已由真机实验更新。当前 Generic、Vader2Pro 与 SCUF 身份的实测及待验证项见 [12-固件实现与验证.md](12-固件实现与验证.md)；Apple 额外键模型和 Elite 拨片限制见 [11-苹果设备模型库-M键原生路径.md](11-苹果设备模型库-M键原生路径.md)。下文的“Elite V2 唯一交付标准”不再适用。

---

## 1. 五条路线对比

| 路线 | 做法 | 拨片 | 可行性 | 主要代价 |
|---|---|---|---|---|
| **R0 零成本实测** | 接收器/有线/蓝牙各模式直接插 Mac，看系统与 GC 是否认 | 无 | — | 10 分钟 |
| **R1 Xbox 360 身份** | 复刻 `Flydigi5Pico`：读接口 0 的 20B XInput，桥成 `0x045E:0x028E` | **无** | **高**（已有同类成品） | 无背键（除非用复合键盘） |
| **R2 One S / Series X 身份** | 跑通 GIP 设备栈，桥成 `0x045E:0x02EA` 或 `0x0B12` | 无（Series X 多一个 Share） | 中 | GIP 要全实现，收益不比 R1 多 |
| **R3 Xbox Elite V2 身份** | 同 R2，PID 换 `0x0B00`，并正确输出 Elite 拨片位 | **有（4 个）** | 中低（唯一未知集中处） | 报告形状/固件格式要对上苹果解码器 |
| **R4 复合设备退路** | 同一个 device 暴露 360 手柄 + 一个 HID 键盘接口；M1–M4 发可自定义按键码 | 语义上"额外按键" | **高** | 游戏必须同时吃键盘；不是真正的拨片 |
| R5 软件 dext | Mac 上写 DriverKit 驱动直接讲 GIP（社区有先例） | 有 | 中 | 需开发者账号/系统扩展授权；与"给小板编程"目标不符 → **仅备案** |

**推荐阶梯（已按决策 D2=拨片硬需求 收紧）**：Phase 0 实测 → R2/R3 的 GIP 管线（先用 Series X/One S 身份验通）→ **R3 Elite V2 为唯一交付标准**。R1（360）只作为**骨架 spike**，用来把双栈/时序/震动跑通，不算交付；R4 仅在 R3 被证伪时启用。

> 提醒：**不要在 GIP 管线验通之前写 Elite 拨片逻辑**。否则一旦失败，无法区分"GIP 会话没通"还是"Elite 解码器对不上"，两种故障的排查路径完全不同。

## 2. 为什么阶梯这么排

- R1 与 R3 **共用同一套 USB 双栈骨架**（Host 读飞智 + Device 伪装），差别只在"输出身份 + 报告格式"。先用 R1 把骨架、时序、双核通信、震动回路全部跑通，风险就从"整条链路"收敛到"只差输出身份"。
- R2 是 R3 的**中间验证点**：先用苹果已验证过的型号（One S / Series X）跑通 GIP 会话，确认"设备端 GIP 脚本 + 报告形状"能被 gamecontrollerd 采纳；再把 PID 换成 0x0B00 并处理拨片位。这样任何失败都立刻定位到"是 GIP 没通"还是"Elite 解码没对上"。
- Flydigi5Pico 的 360 身份已在 macOS 26 上实测可用；本项目在 macOS 27 上要重测一遍（见 05 M1 的验收）。

## 3. 硬件选型

### 首选：微雪 **RP2350-USB-A**（Flydigi5Pico 的目标板）
- 板载 **USB-A**（给接收器）+ **USB-C**（给 Mac），**免焊接**；
- USB-A 走 **PIO-USB** 软件主机（Flydigi5Pico 用 GPIO12/13、`PIO_USB_PINOUT_DPDM`）；
- USB-C 走 RP2350 原生 USB 控制器作 device；
- 双核分工：core0 = Host 栈（读接收器，1kHz 轮询），core1 = Device 栈（对 Mac 输出，1kHz 发送），核间用 **seqlock** 无锁交换。
- 作者实测端到端 ~2ms（这块板 + 这套架构）。

### 备选
- **只有一个 USB 口的 RP2350 板**（Pico 2 / RP2350-Zero / RP2350-Tiny 等）：用 **PIO-USB 走 GPIO** 再外接一个 **USB-A 母座**（微雪另有 RP2350-USB-C / RP2350-USB-CM 的 "PIO-USB 母口版 / 公口版" 与 SpotPear RP2350-One 这类板载 USB-A 公口的板子）。先例工程就是同一思路，只是它的板子自带第二个口。→ **这是"板子型号待确认"（D3）唯一会改变实现细节的地方：PIO 的 DP/DM 引脚号必须按实际板子改。**
- 若 PIO-USB 在本项目负载下抖动不可接受 → **双 USB 控制器 MCU**：STM32F4/F7/H7（OTG_FS + OTG_HS 两个独立核）、ESP32-P4、CH32V307、i.MX RT1062（Teensy 4.x）。代价是换生态（TinyUSB 仍可用，但 Host/Device 双栈例子少）。
- **不要**用单 USB 控制器的 ESP32-S3 之类做"OTG 切换"方案：Host/Device 无法并行，会引入重新枚举与掉帧。

### 工具链（照官方来，不自行发挥）
- **Raspberry Pi Pico SDK 2.2.0**（Flydigi5Pico 已验证版本）
- **pico-pio-usb**（`sekigon-gonnoc/Pico-PIO-USB`，以 submodule 固定 commit）
- **TinyUSB**（随 Pico SDK 提供）
- ARM GNU 工具链 + CMake
- 构建：`cmake .. -DPICO_BOARD=pico2 && make` → 产出 `.uf2`
- 烧录/回滚：BOOTSEL 拖拽 `.uf2`；**回滚点 = 记录原板固件版本，必要时拖回官方 uf2**。刷板不影响 Mac 系统。

## 4. 数据流与时延预算（设计目标）

```
飞智手柄 --2.4G(厂商标称~4ms)--> 接收器 --USB FS--> 小板(host解析) --seqlock--> 小板(device封装) --USB--> Mac
                                                                              目标: 1000Hz, 零丢包
```
- 板内环节（解析 + 跨核 + 发送）目标 ≤ 2ms（先例实测 2ms）；
- 端到端目标 ≤ 8ms，抖动（jitter）优先于均值：**1% low 比均值重要**（这是手柄手感的关键）。
- 震动回程：Mac → 输出报告 → 板 → 接收器 EP5 OUT（8B）→ 手柄。
