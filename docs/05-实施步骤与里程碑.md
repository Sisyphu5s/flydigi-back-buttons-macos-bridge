# 05 实施步骤与里程碑（研究阶段产出的执行计划）

原则：**每一步都有独立验收**；能不动硬件就先不动；任何"看起来成功了"都必须用系统侧证据确认（ioreg / GC 枚举 / 按键位读回）。
目标平台：**macOS 为主，另有 iPad 用户实测可用**。硬件：**Waveshare RP2350**（板级要点见 docs/07）。iPad 结果还没有形成完整的机型、iPadOS、供电、App 和长期稳定性矩阵。

---

## Phase 0 — 零成本前置实测（不需要小板）

目的：确认问题边界，避免为了"其实软件就能解决"的事做硬件。

| 步骤 | 命令/方法 | 期望与判读 |
|---|---|---|
| P0-1 记录现状 | 插接收器 → `system_profiler SPUSBDataType` / `ioreg -p IOUSB -l` | 期望：设备枚举出来（VID 0x37d7/0x2401），但**不会被 GC 采纳** |
| P0-2 换模式 | 有线 USB-C 直连；蓝牙模式（若支持）；若 Space Station 能切 DInput 则切 | 若某个模式被 GC 认出 → 记录其 VID/PID/接口，可能直接改变项目必要性 |
| P0-3 GC 侧看真相 | Safari 打开 gamepad tester；再跑本文件附录 A 的 Swift 小工具 | 判断"枚举了但没输入"的具体表现（GC 无设备 / 有设备无元素） |
| P0-4 采样 USB 描述符 | macOS：`ioreg -p IOUSB -l -w 0` 导出，保存到 `logs/`（待建） | 得到接收器的真实描述符（接口/端点/类），与 docs/02 交叉核对 |
| P0-5 iPad/iPhone 基线 | USB-C 直连或带供电 hub；系统控制器设置和目标 App | iPad 已有成功使用记录；补录机型/iPadOS/供电/App/睡眠唤醒，不能外推到所有设备 |

产出：`logs/P0-*.txt` + 一页结论（哪条路线被选中）。

## Phase 0.5（M0）— 板子热身：先跑通"两个 USB 口"本身

**在碰飞智代码之前必须先过这一关**（否则后面所有失败都无法归因）。

1. 工具链：Pico SDK（先例用 2.2.0）+ ARM GNU 工具链 + CMake；`PICO_BOARD=waveshare_rp2350_usb_a`。
2. 烧 Waveshare 官方 demo **`Host_hid_to_device_cdc`**（USB-A 做 host 收 HID 键盘 → USB-C 做 device 出 CDC）。
3. 把 `pico-pio-usb` 的 `host_hid_to_device` 类示例也跑一遍，确认 PIO host 能枚举设备。
4. **验收**：USB-A 口能枚举一只键盘/鼠标并读到按键；USB-C 口能作为标准设备被 Mac 认到。
5. **同时记录 R12 的实测**：插拔 20 次统计成功率；若出现"插上不认 / 拔了不知道 / 重插失效"→ 照 docs/07 的结论处理（先软绕过，再考虑拆 R13 + 补 15k 下拉，硬件改动属不可逆操作要单独确认）。
6. 记录小板当前固件版本作为**回滚锚点**（BOOTSEL + 拖 uf2 即可恢复）。

## Phase 1（M1）— 复刻 360 桥：打通骨架（**spike，不是交付**）

> 这一阶段有**现成可参考实现**（Flydigi5Pico，同一块板），目标是"我有能力重建它并理解每一行"。
> 按决策 D2（拨片硬需求），**M1 的产物不作为最终交付**，它的唯一价值是把 Host/Device 双栈、时序、核间同步、震动回程全部证伪或证实一遍，让后面 GIP 阶段只剩"输出身份"这一个变量。

1. 引入 `pico-pio-usb`，实现 **Host 栈**：匹配接口（`subclass==0x5D && (protocol==0x81||0x01)`），1000Hz 读 20B XInput 报告，解析为规范化结构体。
2. 实现**物理总线复位**（上电时把 D+/D- 用 12mA 强拉低 200ms 成 SE0）——第三方接收器软复位后初始化不干净，且这块板的 R13 上拉需要它（docs/07）。
3. 实现 **Device 栈**：伪装 360（`bDeviceClass` 建议先试 0xFF，不行再退回 0x00 的已知可用版本；接口 `0xFF/0x5D/0x01`，IN/OUT 中断端点，20B 报告），1000Hz 发送（ZOH 保持最后状态）。
4. 核间 **seqlock** 传状态；震动回程（device OUT → host EP5 OUT 8B）。
5. **验收（必须全绿）**：
   - `ioreg` 显示 0x045E:0x028E 被 Xbox 驱动接管；
   - GC 枚举到手柄（用附录 A 工具打印）；
   - 浏览器 gamepad tester：四轴/双扳机/全部按钮/DPad 对角线正确；
   - 抖动统计：连续 5 分钟无 IN 端点超时，无丢包（板内计数器导出）；
   - 参考对照：Flydigi5Pico 在 macOS 26 上可用 → macOS 27 复测。

## Phase 2（M2）— 打通 GIP 设备栈（先用非 Elite 身份）

1. **反汇编本机 Apple 驱动**（不需要硬件）：
   ```
   otool -tV /System/Library/DriverExtensions/XboxGamepad.dext/XboxGamepad | less
   otool -tV /System/Library/HIDPlugins/ServicePlugins/XboxGamepadHIDServicePlugin.plugin/Contents/MacOS/* | less
   ```
   目标产出：`XboxUSBDevice` / `XboxOneSGamepad` / `XboxSeriesXGamepad` 的**主机侧 GIP 会话脚本**（发什么、等什么、超时多少、`0x04` metadata 内容期望、是否走 `0x06` security）。
2. **与 OGX-Mini 的 GIP host 实现对读**（docs/08 §2 已提取逐字节事实）：`POWER_ON / S_INIT(含 0x06 与 "US") / S_LED_INIT / EXTRA_INPUT_PACKET_INIT(0x4d) / PDP_AUTH`。两份实现互相对齐 → 会话脚本基本可确定。
3. 固件实现 GIP 设备端：命令分派（0x00/0x02/0x03/0x04/0x05/0x09/0x0a/0x20）、NEEDS_ACK 回执、**并接受 `05 20 00 0F 06 ...` 与 `4d 10 00 02 07 00` 这两条主机包**（不要因为不认识就吞掉不回复）、静默不等于掉线。
4. 输入报告按 **18 字节** 发（4B 头 + buttons[2] + 16bit LT + 16bit RT + 4×int16 摇杆），见 docs/08 §3；扳机是 **16 位**（真机 0–1023），不是 8 位。
5. 身份先用 **Series X (`0x0B12`)** 或 **One S (`0x02EA`)** —— 这两条已被社区逐字节验证过（`HIDReportDescriptor.h` 注释里的 `95 12`/`95 11` 之争与修正过程可直接借用）。
6. **验收**：GC 枚举出 Xbox 手柄，**按键/轴值全部能读到**（社区踩过的坑："被采纳为 GCXboxGamepad 但所有元素为 0" = 报告形状不对，不是没连上）。

## Phase 3（M3）— 切到 Elite V2 身份，出拨片

1. PID 改 `0x0B00`（+ `bcdDevice` 选一个自洽固件版本），接口保持 `0xFF/0x47`。
2. 处理 Elite 专属环节：自报固件版本 + 处理主机 `4d 10 00 02 07 00`（Elite raw report 解锁），再按对应格式填拨片位。
3. 把飞智 **M1–M4 → 拨片 1–4**（顺序对齐物理布局；参考仓库的 `M1→P1 … M4→P4` 与"M2/M3 互换以对齐物理位置"的备注）。
4. 其余额外键的归属（按需求定）：C/Z/LM/RM → 或映射到 Elite 已有位/或走 Phase 4 的键盘接口。
5. **验收**：
   - GC 枚举为 Xbox Elite（`GCProductCategoryXboxOne` + 拨片非 nil）；
   - 按 M1–M4 分别点亮 `paddleButton1..4`（用附录 A 工具逐键打印）；
   - Steam Input / 浏览器 / 原生游戏三方都能看到拨片（社区先例是以 Steam 为参照确认 Elite 身份）；
   - 拨片位偏移若有疑问：按 SDL 的 4 种格式（`GIP_BTN_FMT_XBE1/XBE2_RAW/XBE2_4/XBE2_5`）逐个试 + 反汇编本机插件核对偏移。
   - iPad（USB-C）已有一次成功使用记录；继续补测供电、睡眠唤醒、M1-M4、震动、电量和长期运行。

## Phase 4（可选）— 陀螺仪、额外键与体验收尾

- 陀螺仪：GIP 上没有原生陀螺通道 → 两条现实选择：(a) 映射到右摇杆（参考 Linux 驱动的 gyro→joystick 模式），(b) 走 HID 键盘/鼠标接口做体感瞄准；设备侧做简单 IMU 融合（低通 + 灵敏度）。
- 额外键兜底：加一个 HID 键盘接口（复合设备），M1–M4/C/Z/LM/RM 可配成按键码 —— 不依赖 Elite 解码的保底能力。
- 健壮性：热插拔（注意 R12：本板断连检测可能失效）、Mac 睡眠唤醒、接收器断连重连（Host 栈自恢复）、profile 切换（可选转发 `5a a5 a2 03`）。
- 时延/抖动收尾：core0/core1 对齐到固定 1kHz 时间轴（不要用 `now + 1000us` 漂移），每 1ms 采样一次上报。

## 里程碑验收总表

| 里程碑 | 判据（客观） | 失败说明什么 |
|---|---|---|
| M0 | 官方 `Host_hid_to_device_cdc` 跑通：USB-A 认设备、USB-C 被 Mac 认 | 板子/工具链/引脚有问题（先解决硬件层，别写业务代码） |
| M1 | Mac 上出现 360 手柄且所有输入正确 | 双栈/时序/PIO-USB/总线复位有问题 |
| M2 | 出现 Xbox One S/Series X 且元素有值 | GIP 会话或报告形状不对 |
| M3 | 出现 Elite V2 且 paddleButton1..4 独立响应 M1–M4 | Elite 解码对不上（回到 06 R1 的实验矩阵） |
| M4 | 陀螺/额外键/震动/热插拔稳定 | 体验层问题，不影响核心目标 |

## 附录 A：最小验收工具（建议 M1 阶段就写好）

一个本地 Swift/ObjC 小 CLI（20–40 行）：
```swift
import GameController
NotificationCenter.default.addObserver(forName: .GCControllerDidConnect, object: nil, queue: .main) { n in
  let c = n.object as! GCController
  print("connected:", c.vendorName ?? "?", c.productCategory)
  if let x = c.extendedGamepad as? GCXboxGamepad {
    for (name, b) in [("P1", x.paddleButton1), ("P2", x.paddleButton2), ("P3", x.paddleButton3), ("P4", x.paddleButton4)] {
      b?.valueChangedHandler = { btn, _, _ in print(name, btn.value) }
    }
  }
}
RunLoop.main.run()
```
它比任何游戏更早、更精确地告诉我们：设备**是否被 GC 采纳**、**哪些元素为 nil**、**按哪个键点亮哪个拨片**。这是整个项目最高性价比的验收器。

## 附录 B：安全与回滚

- 小板可无限重刷（BOOTSEL + uf2），**不构成不可逆风险**；记录出厂 uf2/固件版本作为回滚锚点。
- **硬件改动（拆 R13、补 15k 下拉）属于不可逆操作**：只在软件绕过确实不够用、且单独确认后才做。
- 不修改 Mac 的系统扩展/SIP/驱动；本项目**不安装任何驱动**（这正是选硬件路线的价值）。
- 不把伪装身份用于对外分发/出售（详见 06 R9）。
- 调试只用只读命令；需要清理后台进程时单独执行并先说明影响面。

## 附录 C：三层验收（2026-09-28 追加，来自 docs/09）

设备的"能用"必须**分层确认**，任何一层失败都要能立刻定位：

| 层 | 工具 | 判据 |
|---|---|---|
| macOS 系统层 | `ioreg -p IOUSB -l` + `hidutil list` | 被 Xbox 驱动接管、HID 节点存在 |
| macOS GC 层 | 附录 A 的 Swift CLI | `GCXboxGamepad` + `paddleButton1..4` 有响应 |
| **Wine/GPTK 层** | Heroic/GPTK 瓶内跑 XInput 测试（思路见 `Tinerou/wolverine-v3-pro-macos-wine` 的 `src/xinput_test.c`）或 `wine control` → Game Controllers | 游戏侧能看到 XInput 槽位与实时值 |

M2/M3 的验收都要**三层都过**（macOS-only 目标的实际交付面就是"游戏里能用"）。
注意两个已知陷阱（docs/09 第二部分）：
- **幻影设备占坑**：调试时若发现 XInput 槽位被"幽灵手柄"占住，先查 macOS 侧是否有残留 HID 身份；
- **拨片在 Wine 层大概率不可见**（XInput 没有拨片概念）→ GPTK 场景的背键要靠键盘映射，这是 M3 之后要单独决定的产品取舍。

## 附录 D：两件不要做的事（来自社区踩坑）

1. **不要为真机做 360 认证**：OGX-Mini 用 `libxsm3` 做真机 XSM3 认证后，360 上不再需要补丁，但**代价是"不再输出到 PC"**。我们目标主机是 macOS → 不要走这条路。
2. **不要把"报告静默"当掉线**：真机是变化驱动；OGX-Mini 曾因此误判断连（把已连接的 pad `tuh_deinit`）。
